Step 01 — Product Understanding

先把接口合同翻译成作者的心智模型

以下五点是后面三套方向共同的地基。如果地基判断错了，三个方向就都错了，请先在这里指出分歧。

1

产品核心是什么

一台只服务于一个人的长篇小说创作台。唯一的产物是作者拥有、并由作者拍板的正文。系统提供的是五种一次性服务——整理历史、生成整章、检查剧情、归档记忆、给方向——而不是五个常驻角色。任何界面元素只用一条标准衡量：它有没有让作者更快回到正文，或更有把握做决定。

2

最重要的创作对象

不是"书"，也不是"任务"，而是当前这一章的正文，以及紧贴它的本章意图。世界观与人物是正文的约束环境，归档记忆是正文的产物，两者都不能反过来占据中心。

竞争时的取舍顺序：正文 › 本章意图 › 本章相关人物与记忆 › 全书设定 › 模型与人格 › 诊断
3

五个 Agent 应该被怎样感知

作者只应感知到三个动作、一个后台事实、一个侧挂能力。角色名只出现在设置里，以及"这条结论是谁给的"这类解释层。

生成这一章Memory Selector → Writer → Checker 是一次动作的内部过程，对外是一句进行时的说明，不是常驻步骤条
复查这一章Checker 单独对眼前这版正文重跑，只给双侧证据，不动一个字
接受这一章作者的明确决定，成立与否与后续归档无关
记忆整理Extractor 在接受之后自行完成，是章节的后续事实，不是作者要盯的任务
找方向灵感创造师侧挂、零副作用、不进主链，失败只影响它自己
4

明示什么，隐藏什么

必须明示这一章是草稿还是已接受；你刚写的字不会被任务覆盖；眼前这个检查结论对应的是不是眼前这版正文；"正文已完成"和"记忆归档失败"是两件事；哪些历史因为你的修改而不再可靠；每个危险动作会连带影响到哪里。
必须隐藏phase／job_id／attempt／revision／schema、轮询、失败候选稿、token、模型名、程序协议、错误机器码原文。技术信息只在作者主动展开"依据"时作为证据出现。
5

两个平台各自承担什么

macOS · 坐下来写完一章

一次两小时以上的连续写作。长正文排版、Bible 与正文对照、Checker 双侧证据比对、长人物卡与长记忆的处理，都发生在这里。键盘是主要输入设备，窗口尺寸变化不应改变信息层级，只改变留白。

iOS · 随身推进一章

三到十分钟的进入：读回上一章、补几句 Bible、抓一条灵感、看那章写完没有、在通勤里接受或重开一章、改几个字。关键流程一个不少，但默认路径是"看与推进"，不是"从零起草"。两端共享语义与状态，不共享空间结构。

Step 02 / 03 — Three Directions

三个方向在信息架构、进入章节的路径、写作区与辅助能力的关系、任务状态的呈现方式上是实质不同的。把配色和圆角全部拿掉，它们仍然是三种产品。

1a手稿 Manuscript — 一本书就是一份连续的稿子

手稿 · Manuscript

没有章节列表，只有一份能一直往下滚的稿子；所有辅助能力都以"页边批注"的方式贴着正文出现，需要时才展开。

视觉气质：安静的纸面。宣纸底、墨字、单一赭石点缀，界面元素几乎全部是细线与留白，没有卡片、没有阴影堆叠。屏幕上最重的东西永远是作者自己的字。

三个动作，44pt 以上。「接着写」在生成中变为「正在成稿 · 取消」；✦ 是灵感（半屏、零副作用）；☰ 是页边（人物 / 记忆 / 检查证据）。

大字体 / 深色：正文字号跟随系统 Dynamic Type，页边浮层在特大字号下改为整屏推入；深色模式用 #14120F 纸底与 #E8E2D6 墨字，赭石提亮到 #C89552。
信息架构
书架（一列书名，无封面无卡片）→ 稿面。书内没有"章节列表"这一层：章脉是稿面的索引不是页面。人物、世界观、记忆、设置都是从稿面拉出的抽屉，退出即回到正文。
macOS 空间
单窗口三段：章脉（88px）· 稿面（固定 600px 版心，右侧常留出批注沟槽，随窗口变化只改两侧留白）· 页边（62px 竖排标签）。窗口拉宽不增加信息，只增加空白。支持多窗口，但一本书一个窗口。
iOS 结构
无 Tab Bar。书架 → 稿面两层。底部意图条 + 三个动作是全部常驻 chrome，其余都是从边缘拉出的临时层。
一章的旅程
打开书直接落在最近创作位置（不是首页）→ 在稿面末尾按「新的一章」，就地长出一个章节标题与空白段落 → 上滑意图条写 Bible、勾选允许人物 → 「生成这一章」，正文保持不动，顶部亮起光带 → 完成时正文以换页动效被替换，页边"检查"标签变绿 → 作者读、改、按需「复查」→ 「接受」在意图条右侧出现，接受后本章标题下方浮现一行"已接受 · 正在整理记忆"，稿面继续向下留出下一章的位置。
人物与记忆
不设资料库首页。人物出现在两个地方：意图条里的"本章允许人物"（勾选＝上限，不是推荐），和正文中被引用时的页边浮层。浮层上半是作者写的固定卡（可编辑，纸白底），下半是归档得出的当前状态与故事线（不可编辑，灰底 + 章节来源）。世界观是稿面最顶端的"卷首"，向上滚动就能读到并编辑。
Agent 出现方式
Memory Selector 从不单独出现，它的产出是页边"记忆 8"这个数字和一份可展开的来源清单；Writer 是顶部光带与章脉呼吸点；Checker 是页边"检查"标签的颜色与正文里的证据下划线；Extractor 是章节末尾一行小字（整理中 / 已整理 / 未能整理，可重试）；灵感创造师是 ✦ 拉出的临时纸片，采用后文字落进 Bible 草稿，可一次撤销。
状态处理
空书＝稿面只有卷首和一句"从第一章开始"；生成中＝光带 + 一行"正在整理历史 / 正在写 / 正在检查"的进行时说明，正文可继续编辑；失败＝正文位置不动，章脉那颗点变琥珀，页边出现一张说明纸片（哪一步失败、正文没有变化、可以重试或修改后重试）；取消＝光带收回，无残留；陈旧＝所有失效的检查与记忆一律降级为灰色虚线，不再声称有效；只读归档＝灰底纸片，不给编辑控件，只给"来自第 N 章"。
强 · 险 · 谁
最强：写作的中心性无可争议，长时间使用最安静，"作品感"最强，也最不像后台。最大风险：结构化操作（人物批量导入、模型设置、归档重试、跨章检索）没有天然的家，容易越藏越深；书多、章多时导航压力全压在章脉上；对"先列大纲后写"的作者不友好。适合：线性推进、边写边想、把工具当稿纸的作者。
纸 · 页边 · 墨 · 赭石
视觉原则：正文宋体 17/2.15，界面苹方 11–13；材质只有两种纸（亮面稿纸 / 暗面页边）；无阴影卡片，只用 1px 细线与留白分区；图标只在动作位出现，其余全部用文字标签；动效只做两件事——换页替换正文、光斑呼吸表示后台在动。
1b台面 Desk — 左手意图，右手正文

台面 · Desk

把"这一章要发生什么"和"这一章写成了什么"放在同一张桌面上互相对照，AI 的每一句结论都必须指着两边的证据说话。

视觉气质：克制的工作台。米白桌面上摊开两页纸，中缝是一条实线。层级靠"纸的高度"而非颜色：正文那页永远最靠上、最亮、最宽。

iOS 结构
三层推入 + 章内横向三面。底部动作坞常驻（意图 / 主动作 / 灵感），主动作按章节状态改写：接着写 → 正在写·取消 → 接受这一章 → 已接受·重开。
一章的旅程
打开书直接进入最近章节工作台 → 右栏写 Bible、勾人物（不写也能继续）→ ⌘↩ 生成，任务带压下来说明"正在整理历史 / 正在写 / 正在检查"，正文原样保留 → 完成后正文原地淡入替换，右栏自动切到"证据"并给出 verdict → 作者改字，证据整块变灰提示需要复查 → ⌘R 复查 → 「接受这一章」，若未通过则弹出后果明确的确认 → 接受后正文变为只读纸面，右栏出现"正在整理记忆"，失败时只在右栏显示"记忆未能整理 · 重试"，正文完成状态不受影响。
人物与记忆
人物在意图栏里以"允许出场"的形式参与写作，点开为一张两层卡：上层固定卡可编辑，下层动态状态与故事线标注"由第 N 章归档得出 · 不可编辑"，视觉上是压在下面的一张暗纸。记忆 8 那一档展示 Writer 这次实际用了哪些历史，每条可点回原章——这是"可追溯但默认不淹没正文"的落点。
Agent 出现方式
Memory Selector＝右栏"记忆"档里的来源清单；Writer＝任务带的进行时句子；Checker＝右栏"证据"档与 verdict 圆点；Extractor＝接受后右栏底部的一行归档状态；灵感创造师＝意图档里的 ✦，展开为盖在右栏上的三张长建议纸片，采用只落进本地 Bible 草稿并显示"可撤销"。
状态处理
每种状态都有固定的位置：进行中在任务带，正文安全性在任务带右侧那句话，结论在右栏，归档在右栏底部，失效在原地转灰。空 Bible 显示三个可行动入口（自己写 / 找方向 / 先导入正文），不显示错误。失败按环节分文案：模型没配好 → 去设置；写作失败 → 正文没有变化，可重试；检查不可用 → 需要你自己决定是否接受；归档失败 → 正文已完成，记忆可以稍后重试。
强 · 险 · 谁
最强：Bible↔正文↔证据的三角关系最清楚，Checker 双侧证据天然有地方放，状态位置固定所以最容易学会；工程落地风险最低。最大风险：最接近"三栏工具"的既有范式，如果右栏默认常开，创作空间会被慢慢侵蚀，也最容易滑向面板堆叠。适合：大纲先行、重设定、需要反复对照检查结论的作者。

时间线就是首页。打开书看到的不是列表也不是正文，而是这本书长到哪里了、哪几段历史需要重整。末端那个赭石点永远是"你该继续的地方"。
「展开写作」是全屏推入。写作层与时间线是同一个空间的两档：从节点放大铺满，退出时缩回原节点，作者永远知道自己刚才在哪一章。
人物游标是 iOS 特有的手势。选一个人物、沿时间线拖动，就能看他在任意一章的状态与故事线——把"人物资料库"变成一次滑动，而不是一个后台。
iOS 承担审阅与决策。接受、重开、重试归档在时间线上就地完成；重开时下游节点当场染上斜纹，后果不需要用文字解释。
减少动态效果：关闭动效后缩放变为直接切换，斜纹与颜色仍然表达全部状态，不依赖动画传达信息。
信息架构
书架 → 编年（唯一的书内首页）→ 三档缩放。没有并列的"章节页 / 人物页 / 记忆页"，人物与记忆都是挂在同一条时间轴上的两种标注。世界观是这条线的起点（第 0 节），设置在书之外。
macOS 空间
单窗口，上方全书鸟瞰条（44px，永远可见）· 左人物线（158px）· 中编年主区（正文就地展开）· 右"这一章留下什么"（262px）。缩放到"正文"档时左右两侧退成 1px 线头，主区成为居中版心；窗口越大，暴露的历史越多，而不是控件越多。
iOS 结构
纵向时间线为主页，节点就地操作，写作全屏推入；底部人物游标条常驻。无 Tab Bar，导航深度两层。
一章的旅程
打开书落在时间线末端 → 按「本章意图」写 Bible、选允许人物 → 「让这一章生长」，末端节点开始呼吸，正文区保留现状 → 完成后新正文从节点内展开 → 「展开写作」进入全屏读改 → 复查结果作为节点旁的一枚标记（通过／存疑／越界／不可用），点开是双侧证据 → 「接受」后节点变实心，右栏的虚线框长出摘要与事实；若归档失败，节点旁留一个空心缺口和"重试"，正文完成状态不变。
人物与记忆
这是本方向最强的一环：人物固定卡是人物线的"起点标签"，动态状态是线上随章推进变化的一串刻痕，故事线就是这条线本身。作者天然分得清"我设定的"和"从正文整理出的"，因为前者在起点，后者在线上。归档事实以卡片挂在对应章节右侧，失效时打斜纹。
Agent 出现方式
Memory Selector＝写作时从上游节点飞向当前节点的几条细线（说明"这次用了哪几章"），静止后成为右栏的来源清单；Writer＝末端节点的呼吸与生长；Checker＝节点旁的证据标记；Extractor＝节点右侧那块"留下了什么"，失败即缺口；灵感创造师＝游标条上的 ✦，弹出为盖在时间线上的三张临时纸片，与主任务互不干扰。
状态处理
斜纹＝不可靠（陈旧记忆、失效检查、重开后的下游）；空心＝还没有发生（未开始的章、未归档的缺口）；实心＝已确定。三种形状覆盖全部状态语义，颜色只是加强。空书＝一条只有起点（世界观）的短线和"写下第一章"；失败＝节点旁的说明条，正文位置永远不动；取消＝节点停止呼吸并回到原大小。
强 · 险 · 谁
最强：长篇连续性、归档语义和"修改历史会向后传播"这三件最难解释的事，在这里是看得见的；重开的后果不需要文案说服。最大风险：最容易滑向数据可视化后台——写作被降格为轴上的一个动作；三档缩放的实现与手势成本最高；章数很多时线会变得拥挤。适合：百万字连载、人物众多、需要反复回改历史的作者。
纸 · 斜纹（不可靠）· 墨 · 当前
视觉原则：形状承担语义（实心／空心／斜纹），颜色只做强调，因此高对比度与色盲模式下信息不丢失；正文宋体 16.5/2.1，年表标注苹方 11；材质只有纸与线两种；图标近乎为零，节点本身就是图形；动效只用于缩放与"生长／染纹"这两种空间变化。

以 台面 1b 为主干，吸收 1a 的克制与 1c 的时间语义

理由有三条。第一，本产品最难的不是"写"，而是"判断"——Checker 的双侧证据、记忆来源清单、接受与忽略的抉择，都需要一个稳定的、和正文并置的位置；1b 是唯一天生具备这个位置的方向。第二，状态位置固定（进行中在任务带、结论在右栏、归档在右栏底部）意味着作者只需学习一次就能应对全部十几种状态，这正是验收标准里最吃紧的部分。第三，它在两个平台上都能不打折地成立，且首版落地风险最低。

必须从 1a 吸收：右栏默认收起，只在有结论或作者主动调用时展开；正文固定版心不随窗口拉伸；正文中的证据下划线代替常驻高亮列表。没有这三点，1b 会退化成三栏后台。
必须从 1c 吸收：用形状（实心／空心／斜纹）而不是颜色表达"已确定／未发生／不可靠"；重开历史章节时，用下游章节被染纹的动画代替一段警告文案；章节轨保留一条极窄的"记忆健康"色带。
需要你决定（我不替你定）
  1. 选哪个方向做深化：主干 1b，还是你更认同 1a 的极简、1c 的时间隐喻？
  2. 目标作者是"边写边想"还是"大纲先行"？这会直接决定意图栏默认开还是关。
  3. iOS 首版是否需要支持"从零起草一整章"，还是只做读、补、判、接受？
  4. 单书 Agent persona：首版只留入口，还是连入口都不放（后端尚不支持）？
  5. 目标字数与 Writer 的 4000 字硬下限如何统一？现在两者语义冲突。
  6. 书多了之后要不要排序／搜索？当前后端没有这些能力，若需要要列入后端增强。
设计假设与后端缺口（不当作已存在能力）
来自合同的事实：无推送需轮询、无搜索分页、无服务端自动保存、无候选浏览、无灵感历史；Persona 支持全局继承与单书覆盖，Extractor 与灵感固定关闭深度思考。
已经落地的设计地基：本地未保存草稿、版本化 Checker 快照与可证明的句子差异由客户端负责；章节列表和书籍读取已有归档健康摘要；失效预览与有效记忆隔离。
现行施工基线：v1.9.3 合同层已经就绪，三个方向只能使用它公开的状态与动作，不得重新引入候选采用、结构化世界观或虚构检查项。
可延后的增强：任务进度推送（替代轮询）、书籍排序或搜索，以及完整的 v2 台面视觉重建。
