# ICTW v2 产品行为合同

> 这是一份与任何既有界面无关的产品语义说明。它回答“用户在做什么、系统应如何回应”，不回答“页面长什么样”。

## 1. 产品本质

ICTW 是个人小说创作工作台。核心产物是作者拥有和最终决定的小说正文；AI 是围绕创作提供记忆整理、整章生成、剧情边界检查、事实归档和灵感辅助的工具集合。

产品不是：

- Agent 管理后台；
- 多人协作文档；
- 通用聊天机器人；
- 自动替作者持续续写的流水线；
- 以模型参数和任务日志为核心的信息系统。

即使系统内部存在五个 Agent，用户的主要心智仍应是“准备一章、写或生成一章、审阅一章、接受一章”，而不是“调度五个机器人”。

## 2. 用户拥有的内容

### 2.1 书

一本书包含书名和世界观。世界观是全书稳定约束，会影响此后写作；改变它可能使旧的生成或检查结论失效。

### 2.2 人物

人物有两层资料：

- 固定人物卡：姓名、角色定位和用户设定，由用户维护。
- 动态状态与故事线：从已接受正文中归档产生，反映人物在故事进程中的当前位置、行动、情绪、持续状态、秘密和关系变化。

用户应能辨认“我写的固定设定”和“系统从正文整理出的历史状态”。不可编辑的归档事实不能伪装成普通文本输入。

### 2.3 章节

一章至少涉及以下概念：

- 标题：可以为空，也是作者已经决定的内容。
- Bible：本章准备发生什么，是 Writer 和 Checker 的剧情权威。
- 作者附注：表达层或写作要求，不替代 Bible。
- 本章允许人物：已知人物可出场集合的上限。
- 当前正文：作者真正看见、编辑和最终接受的文本。
- 归档：正文接受后产生的摘要、关键事实和状态变化。

正文和归档是两个相互关联但独立完成的结果。

## 3. Agent 的产品角色

| Agent | 用户价值 | 不做什么 |
|---|---|---|
| Memory Selector | 从有效历史中整理与本章有关、可追溯的记忆 | 不创造事实，不替作者决定剧情 |
| Writer | 严格根据 Bible 与允许上下文生成完整章节 | 不扩写旧稿，不偷偷增加改变后续剧情的新状态 |
| Checker | 对照 Bible 检查遗漏、矛盾和越界，并给出证据 | 不改正文，不评价文风 |
| Extractor | 从作者已经接受的正文中整理可复用记忆 | 不使用 Bible 或历史补写正文没有发生的事实 |
| 灵感创造师 | 在作者编写 Bible 卡住时给出少量可选方向 | 不进入主写作链，不保存结果，不替作者自动选择 |

Memory Selector、Writer 和 Checker 构成一次写作任务；Extractor 在正文接受后独立归档。灵感创造师始终是侧挂能力。

## 4. 核心用户旅程

### 4.1 建立一本书

1. 用户创建书并填写书名；世界观可以当时填写，也可以以后补充。
2. 用户可以先创建人物，也可以先创建章节。
3. 空书、无人、空世界观都应是可继续行动的初始状态，而不是错误页。

### 4.2 准备人物

1. 用户创建或导入人物固定卡。
2. 用户可以编辑姓名、角色定位和固定设定。
3. 已接受章节形成的动态状态与故事线以历史事实显示。
4. 删除人物是高影响操作：会移除章节关联，并可能使相关写作和记忆失效，必须明确告知后果。

### 4.3 准备一章

1. 用户创建下一编号章节。
2. 用户可以填写标题、Bible、作者附注、目标字数和本章允许人物。
3. Bible 可以为空，但要启动 Writer 时仍必须满足后端人物与输入校验。
4. 选择人物不是“推荐人物”，而是该章可以出现的已知人物边界。
5. 用户可以导入已有正文，或直接在当前正文上手写。

### 4.4 寻找灵感

1. 打开灵感能力本身不读取历史、不请求模型。
2. 用户明确触发后，系统冻结当时的标题、Bible、推进边界和人物选择。
3. 空 Bible、无人选择、前几章历史不足都可以生成；历史不足时自由发想，不能当作完整性失败。
4. 一次得到 3 条方向，公开合同兼容 3–5 条；每条是 200–300 字的连贯剧情可能性，而不是一句梗概或正式正文。
5. 已有标题只是构思锚点，灵感不能替作者另拟标题。
6. 推进边界是硬上限，用于避免关系、秘密或主线跨越尚未发生的中间阶段。
7. 用户选择某条后，只把正文建议加入当前本地 Bible 草稿；不会自动保存，也不会启动 Writer。
8. 用户在等待期间继续编辑时，返回结果属于旧快照，不能无提示覆盖新内容。
9. 失败只表示本次生成失败，不改变章节、Bible、人物或主写作任务。

### 4.5 生成一章

1. 用户明确启动 Writer。
2. 系统依次选择记忆、生成完整正文、执行程序校验并运行 Checker。
3. 任务可能持续较久，用户需要知道系统正在做什么，也应能取消。
4. 生成期间，用户对 Bible、世界观、人物或章节的编辑会使旧结果失效；旧任务不能随后覆盖新内容。
5. Writer 每次从同一输入生成完整整章，不把当前正文当作待扩写片段。
6. 正文按去空白字符计，至少 4000 字且应正常结束；长度或截断失败最多从同一输入完整重写一次。
7. 只有程序校验和 Checker 都明确通过的新稿，才会替换当前可见正文。
8. 失败、Checker 拒绝或 Checker 不可用时，失败候选保留在 Backend 审计中但不展示全文，当前正文保持任务开始前的内容。

### 4.6 手写、复查与接受

1. 用户始终可以编辑当前可见正文；手写后的正文是新的当前内容。
2. 用户可以对当前正文重新运行 Checker。
3. Checker 只给出通过、存疑或越界以及双方证据，不修改正文。
4. 正文或相关输入变化后，旧 Checker 结论立即失效，不能继续显示为当前通过。
5. 当 Checker 未通过、已失效或不可用时，系统不能静默接受；必须让用户明确选择是否忽略检查。
6. 接受是用户的明确决定。成功接受后，章节立刻进入 finalized，正文不再依赖 Extractor 成功与否。

### 4.7 归档与记忆

1. 接受正文后 Extractor 异步启动。
2. Extractor 只读取已接受正文，生成摘要、少量关键事实和必要的章节结束状态变化。
3. 只有整份结果完整通过后才激活；部分、失败或陈旧结果不能进入后续 Writer 记忆、人物故事线或动态状态。
4. Extractor 失败时，用户仍然拥有一章已接受正文。产品应显示“正文已完成，记忆归档失败”，不能把整章描述成失败。
5. 用户可以重试归档，但不能因此重跑 Writer 或 Checker。
6. 有效归档会影响后续章节的记忆和人物状态，因此修改历史章节具有向后传播的后果。

### 4.8 重开历史章节

1. finalized 章节需要明确重开，才能重新编辑或启动 Writer。
2. 重开会取消未完成归档，使当前章已激活记忆失效，并使后续依赖记忆重新失效。
3. 这是高影响但可理解的创作动作，应在执行前说明会影响后续记忆，而不是只用技术术语警告。

### 4.9 导出

- 共享客户端正文导出可选择已接受章节、全部已保存章节或单章，并按章节编号组合为纯文本、Markdown 或逐章文件；可选择附上世界观和人物固定设定。
- 导出只读取已保存版本，不能把尚未保存的本地编辑、临时灵感或失效检查结论混入文件。
- 记忆导出包含章节摘要、关键事实、人物动态状态和故事线，不包含章节正文。
- 正文导出与记忆导出保持独立，不能为了附加记忆而把归档事实混入正文文件。
- 导出是用户拿走自己作品与整理结果的明确能力。

## 5. 状态表达合同

### 5.1 空状态

每个空状态都必须提供下一步，而不是只有“暂无数据”：

- 没有书：创建第一本书。
- 书内没有章节：创建第一章。
- 没有人物：可以创建人物，也可以继续准备无人章节。
- Bible 为空：可以手写、寻找灵感或补充计划；不能把空白等同错误。
- 没有正文：可以写入、导入或启动 Writer。
- 没有归档：区分尚未接受、等待归档、历史 legacy 和归档失败。
- 没有模型配置：引导完成模型设置，不把它包装成内容错误。

### 5.2 等待状态

- 灵感生成是同步等待，但不是主任务，也不应锁住整本书。
- Writer 和 Extractor 是可恢复的异步任务，需要轮询最新 Job。
- 等待状态要同时表达“正在做什么”“当前正文是否安全”“用户还能做什么”。
- 客户端冷启动或换设备后，应从后端重新对账任务，而不是只依赖本地 loading 状态。

### 5.3 失败状态

失败文案至少回答：

1. 哪个环节失败；
2. 当前正文或设置是否已经改变；
3. 用户可以重试、修改、忽略还是无需处理。

Writer 失败、Checker 拒绝、Extractor 失败、模型未配置和网络失败是不同问题，不得合并成无上下文的“生成失败”。灵感创造师作为轻量侧挂能力可以只显示本次失败，因为它没有业务副作用。

### 5.4 陈旧状态

- `outcome_current=false` 的任务结果是历史信息，不能作为当前成功或失败继续提醒。
- 与当前正文不匹配的 Checker 结论不再有效。
- 基于旧 Bible 快照返回的灵感不能直接覆盖新 Bible。
- 历史章节重开或修改后，下游记忆可能是 stale；产品不应继续把它展示为可靠背景。

### 5.5 危险操作

以下操作需要明确说明影响范围，并避免误触：

- 删除书；
- 删除人物；
- 删除章节；
- 重开已接受章节；
- 取消正在运行的 Writer 或 Extractor；
- 忽略 Checker 后接受正文；
- 用新写作任务替换当前在途任务。

确认方式可以由设计决定，但必须使用具体后果语言，不能只写“是否确定”。

## 6. 信息优先级

产品的稳定优先级是：

1. 作者正在创作的书与章节；
2. 当前正文和本章意图；
3. 当前任务是否安全、是否需要作者决定；
4. 与本章有关的人物、记忆和检查证据；
5. 全局／本书 Agent 人格与模型配置；
6. 审计和技术诊断。

这不是页面布局指令，而是发生竞争时的产品取舍。模型名、token、阶段代码等技术信息不能压过正文和作者决策。

## 7. 跨设备与本地状态

- Backend 是书、人物、章节、任务和归档的权威来源。
- 正在编辑但尚未保存的文本、灵感临时结果和一次撤销可以只存在本地。
- 本地状态不能被服务端刷新无提示覆盖。
- 服务端任务结果也不能无提示覆盖用户在任务启动后产生的新编辑。
- 网络恢复、应用重开或换设备时，要重新读取后端并对账；无法证明仍适用的本地提示应降级为陈旧，而不是假装当前。

## 8. 设置行为

- 用户可以维护多个模型 Profile，并分别绑定给五个 Agent。
- Profile 密钥是敏感输入：保存后不回显；更新其他字段不应要求重新输入密钥。
- 用户可以测试模型连接。
- 每个 Agent 有可编辑人格和不可编辑程序协议；设置中必须让两者的所有权区别清楚。
- 五个角色均可为当前书创建人格覆盖；没有覆盖时跟随全局人格。删除覆盖会恢复跟随当前全局值，不保留一份过期副本。
- 单书人格只改变之后启动的本书任务；不能修改模型 Profile、绑定、thinking、effort 或 temperature，也不能影响其他书。
- 参数是否可调由当前模型能力决定。禁用状态应解释原因，而不是留下看似可点但无效的控件。
- Extractor 与灵感创造师固定关闭深度思考，这是产品运行约束，不是用户漏配。

## 9. 设计自由与硬边界

设计可以从零决定：

- 信息架构；
- 导航方式；
- 一屏承载多少创作上下文；
- AI 能力何时出现；
- iOS 与 macOS 是否采用不同空间结构；
- 视觉语言、动效和品牌表达。

设计不能改变：

- Bible 对 Writer 与 Checker 的权威地位；
- 人物选择的上限语义；
- Writer 候选后端私有；
- 只有双重校验通过才自动提升新正文；
- 接受正文与 Extractor 成败独立；
- 灵感创造师不进入主 SOP；
- 程序协议不可被用户 persona 覆盖；
- 陈旧任务不能覆盖当前编辑。

## 10. 未决产品问题

以下问题不应由设计 Agent暗自决定，应作为提案中的显式假设：

- 是否需要新增服务端自动保存、草稿版本或冲突合并；
- 是否需要搜索、标签、封面、分卷或书籍手动排序；
- 是否需要更详细的可观测任务进度或服务端推送；
- 是否需要公开发布之外的导入/导出格式；
- 是否需要把目标字数语义统一到当前至少 4000 字的 Writer 规则。
