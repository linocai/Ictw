# ICTW v2 Clean-room 前端设计简报

## 1. 任务

为 ICTW `v2.0.0` 从零设计一套新的原生 iOS 与 macOS 前端体验。

这不是现有界面的改版、换肤或组件升级。目标是在不改变核心业务合同的前提下，重新思考小说作者如何进入一本书、准备一章、创作正文、调用 AI、审阅结果并维护长期记忆。

设计必须能够让人感到它是一个新的大版本，而不是既有产品的表层视觉调整。

## 2. Clean-room 隔离规则

### 允许读取

设计阶段只允许读取：

1. `01_BACKEND_CAPABILITY_CONTRACT.md`
2. `02_PRODUCT_BEHAVIOR_CONTRACT.md`
3. 本文件

如三份文件存在冲突，以 Backend 能力合同描述的现有能力为可实现边界，以产品行为合同描述的业务不变量为产品边界，并将冲突列为待确认问题。

### 禁止读取

设计冻结前不得读取或检索：

- `App/` 下的任何源码；
- 当前或历史界面截图；
- `archive/design/`；
- 旧版前端设计说明；
- 现有 View、Store、组件、导航或布局名称；
- 旧客户端如何映射后端字段的实现细节。

不得向其他 Agent 询问旧界面长什么样，也不得以继承既有信息架构为前提。若信息不足，提出产品问题或给出明确假设，不得通过查看旧前端补齐。

### 冻结后的交接

只有当用户选定方向、信息架构和关键流程并形成冻结设计后，实现 Agent 才能读取现有工程。届时旧源码只是兼容与迁移材料，冻结设计规范的优先级高于旧 View 结构。

## 3. 产品定位

ICTW 应被体验为一个安静、专注、具有作品感的小说创作空间。

- 小说与作者决策是主角。
- AI 是需要时出现的创作工具，不是持续占据注意力的角色阵列。
- 系统复杂性应转化为清楚的状态与选择，而不是把内部流水线直接暴露给用户。
- 长文本阅读和写作必须舒适；信息密度可以高，但不能像数据管理后台。
- 用户应感到自己掌控作品：系统可以建议、生成、检查和整理，但不会偷偷替他保存、接受或改变剧情。

## 4. v2 体验目标

### 4.1 写作优先

- 进入一本书后，用户能迅速回到最近创作位置。
- 当前章节意图与正文之间的关系清楚，但不会让填写表单压过写作。
- 长时间写作、快速浏览、审阅证据和回顾历史都应各自舒适。

### 4.2 AI 按需出现

- 用户不需要理解五个 Agent 才能完成一章。
- 系统可以用自然产品语言表达“整理历史、生成正文、检查剧情、归档记忆”，技术角色名作为解释层而非主要导航。
- 每次模型调用都由明确意图触发。
- AI 等待、失败和失效要诚实，但不把创作空间变成任务监控器。

### 4.3 作者拥有最终决定

- 自动生成结果不能覆盖任务启动后的新编辑。
- Checker 的证据服务于作者判断，不扮演裁判宣判作品好坏。
- 忽略检查、接受正文、重开历史和删除内容都是明确的作者动作。
- 灵感建议是临时材料，不应显得像系统已经替作者写进作品。

### 4.4 长篇连续性可理解

- 用户能理解人物固定设定、当前状态和故事线之间的区别。
- 用户能知道一章正文是否已接受、记忆是否已成功归档，以及历史修改为何影响后续章节。
- 复杂记忆和来源在需要时可追溯，但默认不应淹没正文。

### 4.5 双平台各自成立

- iOS 不是 macOS 的缩小版；适合短时进入、捕捉、检查、轻编辑和移动阅读，同时仍可完成关键流程。
- macOS 适合持续写作、对照上下文和处理长文本，但不能因此变成面板堆叠的控制台。
- 两端共享产品语义、内容和状态，不要求共享同一种空间结构。

## 5. 创意自由

设计团队可以重新定义：

- 从书架到章节创作的整个信息架构；
- 书、章节、人物、世界观和记忆之间的进入方式；
- 创作模式、阅读模式和审阅模式是否需要明确切换；
- AI 能力的入口、呈现与退出方式；
- iOS 与 macOS 的导航和窗口组织；
- 字体、色彩、材质、节奏、动效和声音是否构成品牌体验；
- 如何让一部作品拥有自己的空间感，而不是一组数据表。

不要先选组件再拼页面。先从作者旅程、注意力和内容层级出发，再决定界面形式。

## 6. 避免的方向

- 不要做成 Agent 控制台、模型 Playground 或聊天机器人套壳。
- 不要把内部五阶段流程做成始终占据主界面的步骤条。
- 不要用卡片网格承载所有内容，也不要形成卡片套卡片的层级。
- 不要以统计数字、任务日志、token 或模型名作为首页核心。
- 不要让用户为了写一章先完成大量设置表单。
- 不要通过大量弹窗解决所有上下文和决策。
- 不要让低对比度、过度装饰、连续动画或极小控件损害长时间写作。
- 不要为了视觉统一强迫 iOS 与 macOS 采用同一布局。
- 不要把尚不存在的搜索、协作、版本历史、服务端自动保存或书级 persona 当作现成功能。

## 7. 必须覆盖的体验范围

设计提案必须覆盖下列场景，但不规定它们对应多少页面：

### 7.1 进入与恢复

- 首次连接后端；
- 无书与创建第一本书；
- 多本书之间切换；
- 回到最近打开的书和章节；
- 网络失败、鉴权失败、模型尚未配置。

### 7.2 作品组织

- 创建、浏览、修改和删除书；
- 世界观维护；
- 章节创建、顺序理解、删除后收拢；
- 人物创建、导入、固定卡、动态状态和故事线；
- 正文与记忆分别导出。

### 7.3 章节创作

- 标题、Bible、作者附注、目标字数和允许人物；
- 空白起步、导入正文和直接手写；
- 未保存本地编辑；
- Writer 启动、选择记忆、写作、检查、取消、失败与成功；
- 任务期间继续编辑导致旧结果失效；
- 应用重开或换设备后的任务对账。

### 7.4 审阅与决定

- 当前正文的 Checker 通过、存疑、越界和不可用；
- 正文或输入变化导致旧检查失效；
- 明确忽略 Checker 后接受；
- 正文接受后立刻完成、Extractor 独立运行；
- 归档成功、失败、部分、陈旧和重试；
- 重开历史章节及其对后续记忆的影响。

### 7.5 灵感创造师

- 打开能力但尚未生成；
- 空 Bible、无人、历史不足时仍可开始；
- 一句推进边界；
- 等待、失败、3–5 条长建议、历史依据与风险备注；
- 采用到本地 Bible、撤销、继续编辑后结果陈旧；
- 与正在运行的主写作/归档任务并存，但不干扰它们。

### 7.6 设置

- 模型 Profile 新建、编辑、删除、密钥不回显和连接测试；
- 五个 Agent 分别绑定模型；
- 模型能力决定 thinking、effort 和 temperature 是否可调；
- Persona 的可编辑部分、默认值和不可编辑程序协议；
- Extractor 与灵感创造师固定关闭深度思考的解释；
- 为未来单书 persona 预留产品方向，但当前不可假装已经保存。

## 8. 状态设计要求

每个核心流程都必须说明：

- 初始状态；
- 空状态；
- 输入中；
- 未保存；
- 提交中或模型等待中；
- 成功；
- 可重试失败；
- 需要修改后重试；
- 被用户取消；
- 因内容变化而陈旧；
- 无权限/鉴权失败；
- 长内容与极端内容；
- 离线或连接恢复。

不要只设计理想成功截图。状态转换及其对正文安全性的解释，是本产品体验的核心组成部分。

## 9. 视觉探索要求

第一轮应提供三个真正不同的方向，每个方向都必须改变信息组织和使用感，而不只是换配色。

每个方向需要说明：

- 核心隐喻与一句话体验；
- 作者注意力如何流动；
- 书、章节、正文、上下文和 AI 之间的空间关系；
- iOS 与 macOS 如何分别成立；
- 典型优势、代价和最可能失败之处；
- 为什么它不是管理后台、聊天套壳或旧前端换肤。

视觉语言应适合中文长文本。至少验证：正文长段落、300 字灵感、Checker 双侧证据、长人物卡、长书名/章名、大字体、浅色/深色、高对比度和减少动态效果。

可以大胆，但不要用无法支撑真实内容的展示型效果冒充产品设计。

## 10. 设计交付物

设计 Agent 的完整交付应包含：

1. **事实与假设表**：哪些来自合同，哪些是设计假设，哪些需要用户决定。
2. **三种概念方向**：具备实质差异、优缺点与推荐顺序。
3. **产品信息架构**：平台共用语义与各平台独立结构。
4. **核心旅程图**：建立作品、准备章节、生成/手写、复查、接受、归档、重开。
5. **状态模型**：章节、任务、Checker、归档和本地编辑如何组合呈现。
6. **关键界面清单**：每个界面的目的、主要内容、首要动作和次要动作。
7. **iOS 方案**：关键尺寸、导航、键盘、大字体和中断恢复。
8. **macOS 方案**：窗口尺寸变化、长时间写作、对照上下文、多窗口或单窗口假设。
9. **视觉系统**：排版、间距、色彩、图标、层级、动效、状态色和长文本规则。
10. **可交互原型**：覆盖主旅程与至少一个失败、一个陈旧、一个危险确认场景。
11. **可访问性说明**：VoiceOver、键盘、焦点、大字体、对比度、减少动态效果。
12. **后端差距清单**：设计依赖但当前合同不存在的能力，按“首版必需/可延后”分类。

在方向获选前，不输出 SwiftUI 代码，不讨论如何改造现有 View，也不以工程复用难度削弱概念探索。

## 11. 验收问题

最终方案应能清楚回答：

- 不解释 Agent 名称，新用户是否仍知道怎样完成一章？
- 用户进入一本书后，正文是否自然成为注意力中心？
- AI 是否只在用户明确需要时出现？
- Writer 失败时，用户是否知道旧正文没有丢？
- Extractor 失败时，是否仍明确显示正文已经接受？
- 用户能否分辨“当前有效检查”和“旧检查结果”？
- 人物固定设定与系统归档状态是否不会混淆？
- 历史章节重开造成的后果是否能用作者语言理解？
- 空书、空章节、无人、空 Bible 是否都能自然继续？
- iOS 和 macOS 是否像同一产品，却各自适合自己的使用环境？
- 方案是否即使拿掉配色和装饰，也仍与旧信息架构明显不同？

若任一答案依赖查看旧前端，说明 clean-room 设计尚未完成。
