## 需求语义（已定，不重新推演）

两个动作的分界线是**保不保留作者写给 Agent 的输入**：

| 对象 | 重写本章 | 删除本章 |
| --- | --- | --- |
| 本章意图 Bible（`user_prompt`）、标题、出场人物选择、豁免名单、作者备注 | **保留** | 删 |
| 正文 `draft_text` | 重跑覆盖 | 删 |
| 归档 revision / canonical facts / state delta / 人物事件 / 状态投影 | 作废 | 删 |
| 章节本身 | 还在，回到可编辑 | 整行消失 |

一句话：重写 = 保留"写给 Agent 的输入"、只推倒 Agent 的产出；删除 = 连输入一起抹掉。

## 已定的设计决策（含理由，不得推翻）

| 决策 | 内容与理由 |
| --- | --- |
| 删除的闸门放服务端 | **仅限本书 index 最大的章节可删**，否则 409。理由是铁律「能程序校验的约束必须程序复检」——上一轮刚修过 `accept` 的同类洞。当前没有任何客户端在调 `DELETE /chapters/{id}`，加闸不破坏兼容。 |
| 重写不设最后一章限制 | 改为知情确认。理由：`reopen_chapter` 与 `patch_chapter` 今天**都没有**任何最后一章限制，作者已经可以打开中间章手改正文触发完全相同的下游级联；把脚本化路径锁死而放任手工路径，闸门形同虚设。 |
| 确认框必须列出具体章号 | 需要一个只读的「重写影响预览」能力（dry-run 复用 `invalidate_downstream_archives` 的判定逻辑）。客户端算不出来——下游失效判定依赖 `prior_state` 投影。最后一章重写时该行不显示。 |
| 成稿章一次确认完成 | 成稿章上点「重写本章」= 一次确认内自动完成 reopen + 带覆盖的生成。确认框已把影响讲清楚，再要求手动先点「重新编辑」只加摩擦不加信息。 |
| 摆放 | macOS：「重写本章」是可见的次级按钮，与现有「重新编辑」并列；「删除本章」收进操作栏新增的「…」菜单。iOS：两者都在右上角章节菜单里，同时给该菜单补上可见文字标签（见下一条）。两端的可用性由**同一个 `V2DeskSnapshot` 字段**驱动，避免两端分叉。 |
| iOS 可发现性 | 顺带修 iOS 阅读器／工作台右上角那个无文字标签的 `ellipsis.circle` 菜单——它是作者这次找不到「重新编辑这一章」的直接原因。iOS 的章节动作继续留在该菜单里，但菜单必须带可见文字。 |
| 铁律 35 保持不变 | 重写时旧正文留到新稿确定性校验 + Checker 双双通过才被提升，失败则旧稿原样保留。⛔ 不得设计成"点下去立刻清空正文"。 |

### 关于 iOS 摆放的说明

macOS 的「重写本章」是操作栏里的实体按钮。iOS 没有对应的常驻次级按钮位：底部 dock 在 v2.0.1 被刻意收口为 `[换面][唯一主按钮][灵感]`，塞第四个按钮会挤压主按钮；导航栏同时放「重写」文字按钮和「更多」文字标签会在小屏上进一步压缩本就 inline 的章节标题。因此 iOS 的决定是：**两个动作都进右上角菜单，而把该菜单本身从"无标签图标"改成带可见文字的入口**，这恰好也是决策 6 要修的那个问题。两端共享同一份 `V2DeskSnapshot.commands` 与同一份确认文案，行为不分叉，只有 chrome 因平台而异。

## 接口契约（本版定死，build 不必再决策）

### 1. `DELETE /api/v1/chapters/{chapter_id}` —— 加硬闸并修正副作用顺序

处理顺序必须是（当前实现的顺序有缺陷，见第 3 步）：

1. `chapter = db.get(Chapter, chapter_id)`；为 `None` 时**直接返回 204**。删除一个已经不存在的章保持幂等，这条必须排在闸门之前。
2. 硬闸：若同书存在 `Chapter.index > chapter.index` 的任意章节，返回 409：
   ```json
   {"detail": {"code": "chapter_not_last",
               "message": "只能删除全书最后一章",
               "details": {"index": 3, "last_index": 7}}}
   ```
   判定用"是否存在 index 更大的同书章节"，不要用 `max()` 相等比较（并列最大值时前者更严格）。这一步必须发生在**任何副作用之前**。
3. 通过闸门后，才执行 `write_registry.get_live` → `cancel(discard=True)` → `thread.join(timeout=8)`。当前实现把这段放在最前面，会让一个即将被 409 拒绝的请求先杀掉正在跑的写作任务。**这是本版必须一起修的顺序缺陷**。
4. 其余逻辑（`db.delete`、`following` 重排循环、`invalidate_downstream_archives(after_index=old_index - 1)`、`rebuild_book_projection`、`commit`、返回 204）保持不变。
5. 保留 `following` 重排循环。硬闸下它不可达，但它是防御性代码，且任何未来放宽闸门都要靠它。

**M6 的因果必须写成代码注释**，别让后人误以为它已被独立修复：`invalidate_writer_inputs` 在本函数中仍未调用；它原本要保护的是"被重排的后续章节仍持有旧 index 下的在途写作任务"，而"仅最后一章可删"让后续章节不存在，缺陷因此不可达。⛔ 将来若放宽闸门，必须同时补 `invalidate_writer_inputs` + `cancel_local_writer_jobs`。本版不得把 M6 记为"已修复"。

### 2. `GET /api/v1/chapters/{chapter_id}/rewrite-preview` —— 新增只读接口

响应 200（新增 `RewriteImpactChapter` / `RewriteImpactPreview` 两个 Pydantic 模型，放 `Backend/app/schemas/chapter.py`）：

```json
{
  "chapter_id": "ch-3",
  "index": 3,
  "affected_chapters": [
    {"id": "ch-4", "index": 4, "title": "第四章标题"},
    {"id": "ch-6", "index": 6, "title": "第六章标题"}
  ]
}
```

- 章节不存在 → 404，沿用现有 `detail="chapter not found"` 文本。
- `affected_chapters` 按 index 升序；只含**真正会被作废归档**的章节，可以是空数组（最后一章、或下游与本章无人物交集、或本章从未接受过）。

实现要求：

1. `previous = archive_input_fingerprint(chapter)`
2. `invalidate_archive_if_input_changed(db, chapter, previous_fingerprint=previous, force=True)`
3. `ids = invalidate_downstream_archives(db, chapter.book_id, after_index=chapter.index)`
4. **在回滚之前**把 `(id, index, title)` 读成普通 Python 数据（回滚会 expire ORM 对象）
5. `finally: db.rollback(); db.expire_all()`
6. 本函数内⛔ 不得出现 `db.commit()`
7. ⛔ 不得复制一份"下游失效判定"的实现。判定必须就是上面那两个真实函数——这正是这个接口存在的理由。
8. 不调用 `stale_archives_for_reopen`（它动 JobRun，与预览无关），不调用 `rebuild_book_projection`（纯写操作，对预览结果无影响）。

为什么客户端算不出来：下游是否失效取决于 `archive_input_fingerprint` 里的 `prior_state`，而 `prior_state` 只覆盖该下游章节**自己选中的人物**、且**不含章节 index**。所以与本章无人物交集的独立故事线不会失效，重排 index 本身也不作废任何东西。客户端没有这份投影，只能算成"全部后续章节"，那是过度上报。

## 风险与回滚

- **最大风险：既有后端测试依赖"删中间章"这条即将非法的路径。** 三个用例必须按 A4 改造而不是删除，尤其 `prior_state_changed` 级联目前全仓只有一处覆盖。改造完先单独跑这三个用例，再跑全量。
- **预览端点会在只读请求里产生数据库写（`invalidate_downstream_archives` 内部 `db.flush()`），SQLite 上短暂持有写锁**，与在跑的 Writer/Extractor 提交存在极小概率的锁竞争。缓解：预览只由明确用户动作触发、耗时毫秒级，且**预览失败绝不阻断重写**（确认框降级为保守文案）。⛔ 不要为了规避这一点去手写一份"下游失效判定"的副本——那才是真正的风险。
- **第二风险：重写是两次网络调用（reopen + generate），中间可能断。** 处理原则已在 B 定死：如实停在"已重开、正文保留、归档已作废"，不自动回滚、不吞错误、不清空正文。
- **第三风险：两端 chrome 不同带来的行为漂移。** 缓解手段是可用性、文案、最后一章判定全部收在共享层，并由客户端门禁的 `require` 守住。
- 回滚范围：本版是一次能力恢复 + 一个只读接口 + 一个后端闸门，**无迁移**。客户端不合格只需回退本版客户端提交与版本号；Backend 不合格回退到 `v1.9.4(45)` 的代码即可，数据库无需任何处理。
