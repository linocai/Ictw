# v2.1.0（Build 47）前后端统一可靠性升级执行计划

状态：施工与本地构建已完成，待发布。此文展开 `PROJECT_PLAN.md` 中的 v2.1.0；主计划是唯一现行版本记录，二者冲突时以主计划为准。发布完成后移入 `archive/plans/`。

## 目标、范围与非目标

- 交付 iOS、macOS 与 Backend 都标记为 `v2.1.0`；双端客户端 Build 为 `47`，Backend 不新造 build 常量。
- 保住既有写作主链：Memory Selector → Writer → Checker → 用户接受 → Extractor。不得恢复 Reviser，不提供候选列表、候选全文或被拒证据。
- 本版必须闭环六项已证实问题：跨端静默覆盖、以设备时钟判定草稿、宁波离线冷启动不可用、不能往返恢复的导出、章节列表 archive health 的非线性查询、破坏性 downgrade。
- 本版仅新增全局搜索与单书 Agent 模型覆盖。标签、分卷、手动排序、推送、软删除、额外作者版本历史和自动全量归档修复都不做。
- 生产发布不属于施工自动动作；须在所有验证完成、用户另行授权后按 `NB_info.md` 执行 Backend-first 发布。

## 稳定产品决定

| 主题 | v2.1.0 决定 |
| --- | --- |
| 内容一致性 | 每个可编辑资源有服务端签发的单调 `content_revision`。v2.1 客户端以条件保存写入；冲突永不自动以本机内容覆盖服务器。 |
| 离线范围 | 允许最后一次成功同步的书架、目录、人物、正文和本机草稿离线打开与编辑；生成、检查、归档、灵感、模型测试、导入和服务器搜索始终要求联网。 |
| 冲突体验 | 同字段或正文冲突保留 base／本机／服务器三份内容，作者明确选择采用服务器或在看过差异后保留本机；仅不相交字段可自动合并。 |
| 本地资料 | 缓存只保存用户可见书籍内容与未同步修改，不保存 API Key、LLM profile 密钥、Writer candidates 或被拒候选证据；设备时间仅用于界面提示。 |
| 备份恢复 | `.ictwbook` 是版本化、带 manifest 校验的项目包；导入永远新建一本书，绝不覆盖既有书。 |
| 搜索 | 全局搜索作者当前可见资料，结果能打开书籍、章节或人物／归档所在章节；隐藏候选和被拒证据既不索引也不返回。 |
| 模型覆盖 | 五个角色均可选择「跟随全局」或整项单书绑定；单书绑定优先于全局，任务开始时冻结实际模型与人格。Extractor、灵感创造师仍由服务端强制有界非思考。 |
| 回退 | 生产回退以已核验的停服前数据库与代码包恢复为主；逻辑数据丢失型 Alembic downgrade 默认拒绝执行。 |

## 接口与数据契约

### 1. 内容 revision 与条件写入

1. 所有作者可修改、会在双端展示的资源均暴露 `content_revision`：Book、Chapter、Character、可编辑 CharacterEvent、全局／单书 Agent Persona、LLM Profile、全局／单书 Agent Model Binding。章节中的人物选择属于 Chapter revision。
2. `content_revision` 在创建时为 1；每一次成功的可见内容变化、Writer 成稿提升、接受／重开／归档状态变化或会改变客户端编辑基线的服务端变化均在同一事务递增。单纯 `last_opened_at` 不递增。
3. v2.1 客户端对已有资源的 PATCH、PUT、DELETE 发送 `If-Match: "<content_revision>"`。服务端收到该头时必须在写入前原子比对；不匹配返回 409 `write_conflict`，仅提供资源类型、ID、提交 revision 与当前 revision，客户端再读取当前公开资源。
4. DELETE 仅在资源仍存在时检查 revision；既有的“已删再删为 204”幂等语义保留。复合动作在同一事务先核验所有参与资源的 revision，再开始任何写入或任务取消。
5. 旧客户端不发送 `If-Match` 的请求在兼容窗口内保持既有语义，绝不能在 Backend-first 阶段被拒。v2.1 客户端必须发送，服务端日志按有／无条件写入记录兼容使用量但不记录正文。公开 v1.8.1 退场之前，不能把该头改为全局强制。
6. 客户端将服务端 revision 作为每份本地草稿及待同步变更的 `base_revision`。彻底移除跨设备 `Date` 与 `updated_at` 的新旧比较；保留时间只作“上次同步”展示。

### 2. 离线缓存、待同步与冲突界面

1. 新建共享的持久资料库，独立于并保留 `LinoI/ChapterDrafts` 目录：缓存书架、每本目录、人物、已读取章节正文和各资源 revision；数据按 schema version 解码，损坏条目只废弃自身并提示重新同步。
2. 正常打开先显示可用的本地快照，再并发刷新服务器；刷新成功以服务端公开资源替换快照，但不可覆盖本机 pending draft。冷启动请求失败时仍可浏览快照并直接恢复本机草稿。
3. 离线编辑产生带 `base_revision` 的持久 pending mutation，页面必须有「未同步」而非“已保存”状态。恢复网络后按资源顺序提交条件写入；成功才更新快照与基线，409 进入 conflict，其他错误保留 pending 内容并给出可重试状态。
4. 冲突先 GET 当前资源。若本地与服务器改动字段不重叠，可基于当前 revision 合并提交；正文、同一字段、删除与引用关系变化必须让作者选择。选择服务器仅移除本机 pending；选择本机必须清楚确认并以刚读取的 revision 再提交，不能暗中强写。
5. 网络限定动作在离线时保持可见但禁用并解释原因；打开灵感页仍不触发请求，只有明确按钮且在线时才请求。缓存操作不得泄露正文给日志或通知。

### 3. 完整项目包与现有导出收口

1. Backend 提供单次聚合读取的项目导出与导入：导出为 `.ictwbook` ZIP，根 manifest 包含格式版本、条目名单、各条目 SHA-256、创建信息与不含密钥的兼容说明；导入先验证路径、格式、大小、条目白名单和每个 hash，再执行恢复。
2. 项目包包含当前书籍、章节作者输入与当前正文、人物固定资料、角色链接、有效 archive v2 的摘要／事实／状态变化、单书人格和单书模型绑定。不得包含任何 API Key、全局模型设置、JobRun、Writer candidate、被拒候选全文或 `draft_evidence`／`bible_evidence`。
3. 导入一律生成新的 Book 与所有下属 ID；重建人物、链接、有效归档和投影，并重新计算输入指纹。导入中的 writing／extracting 在新书中恢复为可编辑、无在途任务的状态。引用不存在全局 Profile 的单书模型绑定不导入为有效绑定，改为报告并回退全局，不阻断书籍内容恢复。
4. 当前正文／记忆文本导出改为同一服务端聚合读取路径，双端不再逐章请求。iOS 在文件完全生成并经过 manifest／写入校验后才打开系统分享；macOS 复用同一数据源保存。取消只取消本地传输，不产生半导入。

### 4. 全局搜索

1. Backend 维护可重建的全文检索索引，按书籍范围查询并支持全库查询。查询、排序、分页、片段截断和转义由服务端确定；客户端不得下载全量正文再自行搜索。
2. 可索引内容仅为作者当前可见的 Book 标题／世界观、Chapter 标题／作者输入／当前正文、Character 名称／固定设定，以及有效 archive v2 的摘要与事实。inactive、partial、failed、stale archive 和所有隐藏 candidates／被拒证据一律不入索引。
3. 搜索结果返回受限片段与稳定定位信息（book、可选 chapter、可选 character、结果类型），不返回不在结果上下文所需的全文。双端分别跳转到书架、章节阅读／工作台或人物详情；离线时明确提示服务器搜索不可用。
4. 索引创建、接受、重开、人物／书籍编辑、删除、项目导入与 archive 激活／失效必须在同一事务同步更新；迁移后从现有安全可见数据全量构建一次。

### 5. 单书 Agent 模型覆盖

1. 为五个现有角色新增 BookAgentModelBinding；一行代表该书该角色的完整绑定覆盖，缺行即完全继承全局，避免字段级半继承的不可解释状态。覆盖包含所选现有 Profile 与该角色的 thinking／effort／temperature 配置，不复制或导出 Profile 密钥。
2. 每次读取都返回 `source`、单书值、全局值和经 capability／程序规则处理后的 effective 值。两个客户端在本书 Agent 设置中展示“跟随全局／本书覆盖”和实际模型、思考、effort、temperature。
3. 选择或编辑单书绑定使用同一 capability 校验与安全清洗；Extractor 与灵感创造师无条件报告及执行 `thinking=false`、`effort=nil`，无法关闭 thinking 的模型仍返回 409。
4. 任务创建时一并冻结实际 Persona 与实际 Model Binding；之后改全局或单书设置不得改变在途 Writer、Checker、Extractor 或灵感任务。

### 6. Archive health 性能与回退保护

1. 章节列表不得再对每章调用会回溯历史的 `archive_input_fingerprint`。新的列表级计算按书／章节顺序批量预取 active revision 与 delta，以一次滚动投影得到等价的有效性判断；详情、接受、重开与修复路径仍可使用严格单章验证。
2. 查询数量必须对章节数保持固定上界，不能以“本机很快”为验收。测试用合成的长书和 SQL statement 计数守卫证明列表读取不会退化为每章回溯。
3. 所有会丢失逻辑数据的 Alembic downgrade（至少 archive ledger、book persona 与本版新表）默认在 DDL 前 fail-closed。唯一允许的人工路径必须先有外部、可核验的停服前数据库备份 manifest，再显式给出一次性生产授权；没有两者，`alembic downgrade` 失败且数据库保持不变。
4. 发布回退文档与预检以“停止服务、恢复已核验备份和旧代码”为标准路径，绝不把 destructive downgrade 当常规回退。运行迁移的 `upgrade` 仍只通过 `alembic upgrade head`。

## 验收门槛

1. 两个 v2.1 客户端对同一书、章、人物、Persona／模型设置编辑时，后一笔旧基线写入必为 409；任何冲突分支都能保留本机内容或采用服务器内容，不能静默丢字。
2. 断网冷启动仍能打开最后同步的书架、章节和正文；本机草稿可打开和编辑；恢复连接后成功同步或进入清晰冲突，绝不按设备时间决定覆盖。
3. `.ictwbook` 可在隔离数据库导入为新书，正文、人物、链接、有效归档和投影一致；篡改 manifest／条目／hash、隐藏候选字段或路径逃逸均拒绝且无部分写入。
4. 搜索能命中授权范围内的书籍、正文、人物和有效 archive，能准确跳转；回归测试证明 candidates、拒绝证据、非有效 archive 永不出现在索引、结果或日志。
5. 单书模型绑定与全局回退的 effective 值在 API、iOS、macOS 和任务冻结记录一致；两个 bounded 角色无论界面配置如何都不会启用 thinking。
6. 长书章节列表的 SQL statement 上界不随章节数线性增加；其 archive health 与严格详情判断一致。
7. 无授权 downgrade 的任意破坏性路径在第一条 DDL 前失败；明确授权且存在核验备份的受控演练可完成，并优先验证备份恢复路径。
8. Backend 全套 pytest、Alembic 唯一 head、客户端状态测试、iOS Release 与 macOS Release 构建均通过；iOS／macOS 分别在不共享 DerivedData 的条件下构建。

## 兼容、发布与风险

- **Backend-first**：先部署可同时服务旧协议与新协议的 v2.1.0 Backend 和 migration，再换装 v2.1.0 客户端。旧 v1.8.1 因未发送 `If-Match` 继续可用；新客户端立即享受冲突保护。不得在此版本删除 `chapter_style`、旧 `summary` 镜像或改变隐藏候选限制。
- **部署前数据保护**：按 `NB_info.md` 停服、备份 `linoi.db`、核验 integrity／foreign keys／head、检查单实例和鉴权 health。生产过程不得打印 `KEK_SECRET`、`APP_TOKEN`、数据库正文或模型密钥。
- **SQLite 与迁移风险**：导入、FTS／搜索索引创建和 revision backfill 必须是原子迁移，并针对现有生产数据规模做演练；失败后走备份恢复，不能尝试无保护 downgrade。
- **本地缓存风险**：缓存不是服务器真相。用户可随时清除本机缓存；待同步内容不能被清缓存流程静默删除，必须先确认或导出本地恢复资料。
- **模型风险**：单书模型绑定只引用已有全局 Profile，不创建第二套密钥存储；Profile 删除或不可用时在任务启动前给出安全错误，不能把请求转发到未知地址。
