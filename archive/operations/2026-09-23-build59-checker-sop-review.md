# Build 59 Checker 与小说生产 SOP 审查

审查日期：2026-09-23。用户要求只 Review，不修复、不部署。

范围：生产标签 `v2.1.1-build59` / `e7b14b02301ae87b70c3ee56c823e9277cbe9184` 的当前行为，以及 HEAD `b342d42225aa13df7316dfe3a9b01d052723da66` 的发布收尾记录。开工工作区干净；这是现行实现审查，不是把空 diff 当作审查通过。覆盖 Selector → Writer → Checker → 接受 → Extractor、相关双端共享呈现与恢复入口。未修改程序、未调用真实模型、未重提真实章节。

结论：存在误拦、漏检及恢复路径不完整。只改提示词不能修复程序中的这些行为。下列条目区分实现缺陷与需要调整产品规则的设计问题；不把既定的候选隐私、人物授权或原子归档原则本身当成缺陷。

## Checker 与正文接受

### C1 — P2：没有有效证据仍能拦截，结论与问题列表也未保持一致

`Backend/app/services/write_jobs.py:325` 的结果校验只检查若干字段非空，不核对引用是否实际存在于正文或 Bible。`suspect + []` 原样保留；`violation + 无有效问题` 降为 `suspect`；两者在 `:478` 后仍阻断新稿。反过来，`passed + 非空冲突 issues` 会按 passed 提升正文。

影响：模型没有提供可核实问题，也能挡住一章；伪造引文可被当成证据；互相矛盾的结构化结果还可能被放行。合成结果验证已确认这些分支。应先区分“检查服务输出无效”和“正文有问题”，核验引文来源，并统一 verdict 与 issues 的契约；不能用猜测给出正文违规结论。

### C2 — P2：非空 Bible 时，所有问题都被强制要求 Bible 引文

`Backend/app/services/context.py:631` 要求每个 issue 同时引用正文和 Bible；`write_jobs.py:334` 强制执行。可是检查任务还包括世界观、人物卡、章前状态、历史及正文内部矛盾。这些问题不一定在 Bible 中有对应内容。

影响：诚实报告非 Bible 事实冲突、把 bible_evidence 留空的结果会被丢掉，随后变为没有具体问题的 suspect，仍然拦截。应按问题种类标记真实依据来源，不能为了通过格式检查逼模型从无关 Bible 里找引文。空 Bible 分支已放宽，不代表非空 Bible 的此问题已解决。

### C3 — P2：人物硬拦截把普通词语也当作人物出现

`Backend/app/services/context.py:641` 按全书人物姓名做子串匹配；两字及以上没有语义或词边界判断，单字只有左侧汉字启发式。确定性复现：“夏天”命中“今年夏天天气很热”，“白雪”命中“窗外白雪皑皑”，“林”命中“林业改革”。

影响：Bible、生成正文、导入稿都可能被错误识别为未授权人物；接受入口的这类失败不可强行忽略。人物授权规则可以保留，但弱匹配结果不能直接当作已经证实的出场事实。

另一个已复现的出口缺口：同书两个人物同名时，歧义检查在豁免之前返回；把姓名加入豁免名单也不能解除 ambiguous 拦截。当前提示所暗示的“选择或豁免”并不能覆盖这种情况。

### C4 — P2：作者短稿允许接受，却无法先完成 Checker 检查

`Backend/app/routers/chapters.py:834` 将全部 `draft_violations` 作为 `/check` 的前置阻断，其中包含不足 4000 字。该标准本来用于 Writer 产出，接受入口则允许作者显式确认短稿。

影响：用户自己写好的短章节不能先检查事实与剧情，再决定接受；只能走忽略分支。应将生成长度要求、作者接受确认和是否可进行内容检查分开。这是现有规则的设计冲突，已有测试也在固定这一行为。

### C5 — P2：Checker 暂时失败后，无法单独重查已经生成的新稿

`Backend/app/services/write_jobs.py:469` 将模型故障记为 unavailable，`:525` 后恢复旧正文；新稿只在后台 candidate 留档。公开 `/check`（`chapters.py:835`）检查的是当前可见正文，而不是这份未提升的新稿。前端失败恢复走重新生成。

影响：Writer 已经完成几千字，只因 Checker 超时或格式出错，恢复却要重新调用 Writer，花费时间并丢失这次稿件的可恢复价值。候选不公开可以继续保留；缺的是后台对同一份不可变稿件重试 Checker 的恢复动作。

### C6 — P2：新导入稿可从 API 绕过 Checker，不限于历史兼容稿

`Backend/app/routers/chapters.py:1021` 只有存在 candidate 才强制当前 Checker passed 或明确 override。新的 import/手贴稿同样可能没有 candidate；达到长度且人物检查通过后，直接 `/accept` 即可接受，不要求已经检查或明确忽略。

影响：所谓 pre-v1.6 兼容分支覆盖了现在的新稿，服务端流程缺口仍在。当前客户端通常先要求检查，所以这不是“正常前端每次都跳过”；它是实际存在的 API 合同漏洞。应使用可靠的历史兼容标识，而不能用 candidate 缺失代表旧数据。

### C7 — P1：手动检查等待模型期间持有 SQLite 写锁

`Backend/app/routers/chapters.py:846` 对首次检查的新稿先创建 candidate 并 flush，再请求模型，直到 `:891` 才 commit。`Backend/app/agents/checker.py:46` 的模型等待配置为 180 秒；这期间写事务一直没有结束。

隔离并发复现：一章的假 Checker 暂停等待时，另一章保存等待 5.23 秒后返回 HTTP 500；放开 Checker 后原检查才返回 200。影响不局限于该章，会波及其他数据库写入。应把远端调用移到写事务外，返回后在短事务内复核 revision/输入快照再保存。

### C8 — P1：检查有效性的指纹与真实检查上下文不一致

`Backend/app/services/context.py:33` 的指纹包括人物全书当前 dynamic_fields，却不包括实际使用的历史摘要/事实、上一章结尾与章前投影；真正的手动检查上下文在 `:580` 构造。

隔离 API 复现：检查后修改前章历史摘要，使参考事实发生相反变化；后章实际 reference_context 已变，指纹仍相同，服务端仍返回原来的有效 passed。反向也存在错误失效：后章改变全书人物当前状态，即使早章的章前输入未变，也会改变早章指纹。

应基于真正冻结的检查输入及其来源版本判断有效性，不能使用另一组近似字段。正文和 Bible 相同不代表检查依据仍然相同。

### C9 — P2：程序认可的豁免没有进入模型的授权上下文

`Backend/app/services/context.py:693`、`:729` 在确定性检查中扣除豁免姓名；但 `:441` 构造 Writer/Checker 白名单只使用已选人物，固定协议仍禁止白名单外人物。豁免也不在 `draft_fingerprint` 中。

影响：有豁免数据的章节可通过程序预检，模型收到的规则却仍说该人物未获授权，存在重复拒绝的指令冲突。旧界面的 `exemptAndRetry` 会写入这个字段，但当前 V2 不能据此假定已经提供相同入口。应让实际授权集合在预检、模型上下文、检查有效性判断中一致；这不等于取消人物权限。

## 记忆选择与上下文

### M1 — P2：没有历史的第一章仍依赖 Selector 成功

`Backend/app/routers/chapters.py:590` 总是解析 Selector 配置，`:647` 总是创建该 Agent；`write_jobs.py:370` 随后调用，未以候选是否为空判断。

隔离 API 复现：新书第一章、没有历史、Writer 可用，Selector 返回错误后任务 failed，Writer 调用次数为 0。这里没有历史可选择却多了一项阻塞条件。应对无候选情形走确定性的空历史结果，同时保留有历史时的错误处理。

### M2 — P2：已经识别出的历史冲突没有进入 Writer/Checker

`Backend/app/services/write_jobs.py:377` 校验并保存 `selection.conflicts`，但 `:403` 构造两者共同上下文时只传 memories 与 previous_ending。当前 V2 页面也没有接入旧界面的记忆冲突面板。

隔离 API 复现：Selector 只在 conflicts 返回“城门已在旧章永久焊死”，任务保存了这条冲突，Writer 与 Checker 的实际输入均没有这条信息，任务仍正常结束。

影响：系统已经发现的连续性矛盾既不能帮助生成与检查，也没有形成明确的作者处理动作。不能把“已存审计记录”等同于“创作流程已经处理冲突”。应传递带来源的冲突，并明确其与作者本章意图的处理方式。

### M3 — P2：提示预算与实际预算不一致，会整条丢掉合规记忆

`Backend/app/services/context.py:299` 告知简报最多 2400 字、上一章结尾独立最多 700 字；实际 `write_jobs.py:374` 从同一个 2400 预算扣去结尾，`context.py:423` 对超出的整条简报直接跳过。

确定性复现：700 字结尾加一条 1800 字简报，符合提供给模型的简报限制，实际却保留 0 条简报。无效来源 ID 的条目也在 `:412` 静默跳过；没有区分“没有相关历史”和“模型输出被程序全部丢弃”。

影响：Writer 和 Checker 在缺少关键历史时继续工作，后者也无法发现依赖该事实的矛盾。应统一预算，并对重要条目被丢弃提供校正或明确的降级状态，而非静默当作无需记忆。

### M4 — P1：归档事实被替换时，在途写作没有完整失效

`Backend/app/routers/chapters.py:616` 在任务启动时快照历史候选。`Backend/app/services/archive_v2.py:505` 却只从状态 delta 收集 updated_character_ids，`write_jobs.py:681` 仅撤销选择这些人物的写作任务。

触发条件：前章新归档只改变 summary/facts，没有 delta，或后章依赖的是章节级事实而未选择这些人物。此时后章任务继续使用旧历史，generation 没被相应撤销，仍可能提升正文。Writer 和 Checker 共享同一旧快照，并不能证明提交时其历史依赖仍有效。应持有并复核实际记忆 revision 依赖，或采取明确的同书后续任务失效策略。该项为代码路径确认，未在真实生产环境并发复现。

## 归档与连续生产

### A1 — P1：归档模型配置失败会提前阻止正文接受

`Backend/app/routers/chapters.py:1001` 把 Extractor client 放在 `/accept` 前置依赖中；`Backend/app/llm/factory.py:47` 的未配置、密钥不可解密、模型不能关闭 thinking 等错误会在 `chapter.status = finalized` 之前返回。

影响：已经写好且满足接受条件的正文，因为后续记忆整理的配置问题不能完成接受。这与正文接受和归档独立的产品承诺不一致。应先独立确定并保存接受结果，再将归档启动问题记录为可恢复的归档失败。

### A2 — P2，设计与错误分类：值不完全相同被直接称为实质冲突，并使整个归档不可用

`Backend/app/services/archive_v2.py:384` 只比较同一状态槽的 `(operation, value)` 是否相等；不同字符串即 `conflicting state delta slot`。程序没有证明语义矛盾，也没有区分同义描述、补充描述与章内过程/章末状态。

因此截图只能证明模型给同槽提供了不同值，不能据此断言小说本身存在矛盾。原子激活完整归档有合理性；问题是没有先做可靠的重复归并/章末收敛，也没有无法收敛时的局部纠正路径，直接让摘要、事实、状态一起不能使用。不能简单取最后一项来冒充解决冲突。

即使一个状态项确实无效，整份已提取摘要/事实也无法进入后续写作，是现行 all-or-nothing 规则的生产代价。可以评估把已验证叙事事实与状态投影分开管理；这是产品契约变更，不是本轮可擅自实施的普通修补。正文句子顺序也不一定等于故事时间顺序，不能单凭证据位置自动断定“最后一条一定正确”。

### A3 — P2：归档失败缺少可定位证据，重试只是重新抽取

`Backend/app/services/write_jobs.py:779` 的失败处理只保留 summary 与错误原因，没有保存被拒的事实/状态项及关联证据定位；校验遇到第一个错误即停止。`archive_v2.py:59` 只把少数原因翻译成中文，其它原因仍可能直接透出英文。

影响：用户只能看到“冲突/失败”，不知道哪个人物、哪个槽、哪两条记录；后台也无法核实这次是否同义。归档重试不携带这次具体问题，可能反复付费重抽而无法收敛。应保留受控、可诊断的失败证据和准确恢复说明；不需要把真实正文或完整模型输出写入公共日志。

### A4 — P2：完全相同内容仍有未去重就整包拒绝的路径

`Backend/app/services/archive_v2.py:234` 先限制原始数组数量，再执行状态去重；因此 19 条完全相同的 delta 仍超出 18 项上限。`:291` 对完全相同的 canonical fact 仍直接报错，未归并其引用。

两种均已合成复现。Build 59 修复的是限额内状态槽重复，不是所有完全相同条目的重复。应在保证证据与引用有效的前提下规范化、重映射和去重，再按有效项限额；无需扩大产品允许的事实数量。

### A5 — P2：占位词的子串封禁会误伤完整有效的状态

`Backend/app/services/archive_v2.py:332` 只要 value 含“未知、未明确、暂无”等任何一项，就拒绝整份归档。隔离复现：“当前目标＝调查身份未知的来客”被拒，虽然人物目标本身明确，并非模型用“未知”占位。

应区别整个值只是占位内容，和一个完整状态描述里自然包含这些词。继续禁止编造/占位，不代表任意包含这些字样的句子都无效。

### A6 — P2，SOP 缺口：带着缺失记忆继续写作，没有明确降级提示

`Backend/app/services/context.py:133` 排除无有效归档的章，但可能保留紧邻上一章结尾；`chapters.py:584` 的写作入口没有检查历史归档完整性。`App/LinoI/V2Shared/V2DeskPresentation.swift:519` 对已接受章提供开始新章。

原章节有归档失败提示，这点已修复；缺口是进入后章写作后，没有明确告知这次缺少哪些摘要、事实和状态，检查结论也不标记这一限制。应让作者知道并选择先恢复或在已知降级下继续，而不是新增一律禁止写作的硬门禁。

### A7 — P2，SOP 缺口：多章归档失效后没有按依赖顺序恢复的引导

`Backend/app/services/archive_v2.py:628` 会使依赖前置状态的后续归档 stale，`chapters.py:1071` 提供单章重试。用户可以先重试更后的章节；它基于缺失的前章状态完成后，前章恢复又会使它再次 stale。

存在单章恢复入口，不是无法恢复；问题是缺少依赖顺序提示，容易无效重复提取。可提供下一项应恢复的章节或明确的逆序警告。任何批量恢复仍应尊重历史重提的精确授权与正文哈希限制，不应后台自动重提全书。

### A8 — P2：归档健康汇总忽略“旧归档仍有效，但最近重试失败”

`Backend/app/services/archive_v2.py:570` 保留旧 active 时，章节 aggregate status 仍为 complete；读模型返回了 latest_attempt_status。可是 `App/LinoI/V2Shared/V2DeskPresentation.swift:488` 的归档状态只凭 complete 显示完成，章节轨及 `Backend/app/routers/books.py:269` 的健康计数也没有反映最近失败。

即时任务失败 banner 仍可能正确显示，不能声称所有错误提示都消失。确定的缺口是持久的归档健康汇总无法区分“本次成功”和“本次失败、继续使用旧记忆”。应同时表达旧归档可用与最近尝试失败，避免作者误判更新已经生效。

## 不应误当成缺陷的现行行为

- 空 Bible 已跳过相对于本章写作要求的检查，仍检查有资料支持的事实问题；不能再把 Bible 为空本身列为本版问题。
- 正文接受后，运行中的 Extractor 失败不会撤销正文；单独归档重试不会重新跑 Checker。A1 是归档启动前的配置依赖缺口。
- 完全相同的状态增量在 Build 59 已能去重。不能把截图当成该修复未部署的证据。
- 未通过归档不得进入有效记忆、候选不公开、真正的未授权人物不能无条件接受，均有明确产品依据；审查不建议直接取消这些原则。
