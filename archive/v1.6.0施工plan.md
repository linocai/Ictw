# ICTW v1.6.0 写作架构升级执行记录

> 主计划：[`PROJECT_PLAN.md`](../PROJECT_PLAN.md)；本记录展开 v1.6 系列施工契约。状态：`v1.6.0(15)` 已发布，`v1.6.1(16)` 补丁发版执行中。

## 1. 已确认的产品决定

1. 现役链固定为 **Memory Selector → Writer → Checker →（用户接受）→ Extractor**。彻底删除 Reviser，不以任何名称保留其自动修文、扩写、压缩、模型绑定或设置入口。
2. `user_prompt` 是本章 Bible 原文。它从章节快照直接交给 Selector（仅供相关性判断）、Writer 和 Checker；任何 Agent 返回值均不得替换、改写或概括它。
3. 章节编辑页只提供 Bible（及标题、允许人物）。目标字数与本章备注从 v1.6 双端写作界面、Writer 输入和流程移除。
4. Writer 一次完成整章，不按场景拼接、不在旧稿上扩写。允许文学性的动作、对话、心理、环境和自然衔接；不得新增会改变后续事实的剧情、人物、线索、秘密、冲突或关系变化。
5. 正文长度只要求去空白字符数 `>= 4000`，没有产品上限；输出必须 `finishReason=stop`（兼容上游等价的正常结束值）。少于下限、空正文或截断时，仅从同一输入快照完整重写一次；绝不把短稿交给 Writer 扩写。第二次仍失败即停止并说明原因。
6. 人物选择仍是允许出现人物集合的上限。Bible 预检和正文人物程序复检仍保留；这不是字数规则的一部分，不能因 v1.6 放松。
7. Checker 只举证，不改文。结论为 `passed`、`suspect` 或 `violation`；用户可在看到证据后重生整章、手动编辑／重新检查或明确忽略后接受。
8. Extractor 只处理用户接受的实际正文，产出更长章节摘要、状态变化、未决事项及原子记忆；不得用 Bible 补写正文未发生的事实。
9. 四个 Agent 的默认人格词全部重写；人格词可编辑，程序协议不可编辑且始终追加。设置页只显示现役四 Agent，并展示可编辑人格词、只读协议、绑定模型及实际生效的思考／温度配置。

默认人格词的职责边界固定如下，Builder 不另行发明角色：

- **Memory Selector**：严谨的小说记忆编辑，只压缩有来源的历史事实，绝不推断或续写；
- **Writer**：服从 Bible 的中文小说创作者，文学自由只在表达层，不新增剧情状态；
- **Checker**：克制的剧情边界审计员，只举证 Bible 遗漏、矛盾和越界，不评文风；
- **Extractor**：忠实的小说档案管理员，只归档接受正文中真实发生的内容。

对应固定协议分别保证 JSON 形状与来源、Bible 原文优先和整章纯正文、证据化三档结论、以及“正文而非 Bible”事实来源。这些协议不出现在可编辑文本框中，但须在设置页完整只读展示。

## 2. 数据与兼容契约

### 2.1 保留的旧字段

- `chapters.target_word_count`、`author_note` 与响应镜像 `chapter_style` 暂不删列、不删 wire 字段，历史值原样保留；v1.6 不显示、不写入流程、不放进预检、Selector、Writer、Checker 或 Extractor Prompt。
- 新客户端创建／更新章节不再发送前两项；后端仍接受旧客户端的字段并返回它们，保证 v1.5 及更早客户端可继续解码。`chapter_style` 兼容窗口仍按仓库规范执行。
- 旧 JobRun、LLM audit 与历史正文不得被迁移删除；仅遗留 `reviser` 的 persona/model-binding 配置删除，历史审计角色保持只读可追溯。

### 2.2 新迁移（单一 Alembic head）

建立一条 v1.6 migration，先做 SQLite foreign-key 检查；迁移只通过 `alembic upgrade head` 执行：

- `job_runs` additive 增加 `memory_context`、`checker_result`、`bible_sha256` 和 `draft_fingerprint` JSON／文本元数据；不存原始 Prompt 到 LLM 审计表。
- 新建 `chapter_draft_candidates`：保存每次 Writer 原样候选、所属 job／尝试序号、去空白字数、finish reason、确定性校验、Checker 结果、创建时间和可选的当前标识。候选不会互相覆盖；`chapters.draft_text` 保持当前可编辑／兼容正文。
- 删除 `agent_personas`、`agent_model_bindings` 中 `reviser` 行；为 `checker` 插入 persona 与 binding（初始复制 Writer 的 LLM profile，具体思考／温度由其 binding 独立保存）。
- 仅当旧 persona 文本等于已知旧默认值时替换为新默认人格词；用户自定义人格词不丢失，可在新界面主动「恢复 v1.6 默认」。

迁移前后的生产门禁：备份 `linoi.db`、`PRAGMA integrity_check`、`PRAGMA foreign_key_check`、`alembic current/heads`；不得使用启动时 `create_all` 或 SQLite 全表重建来绕过迁移。

### 2.3 API

现有 `GET /chapters/{id}/job` 和 `WriteJobStatus` additive 返回：

- `memory_context`：最终给 Writer 的记忆简报、上一章承接片段、来源 ID／章节／类型／实际摘录及字符统计；不是 Selector 的原始候选选择。
- `checker_result`：结论、检查正文指纹、问题列表；每项包含类别、正文证据、对应 Bible 证据及克制的理由。
- `draft_candidate`／候选元数据：当前任务产生的候选，而不是把所有正文塞进轮询响应。

新增受鉴权保护的候选列表／选择接口，以及只运行 Checker 的检查接口；接受接口增加显式的 Checker 决策。默认接受要求正文对应一份当前 Checker 结果；只有用户明确选择「忽略检查并接受」时才允许覆盖 `suspect`、`violation` 或检查不可用状态。任何正文手动编辑、Bible／人物／世界观变化都会使旧检查指纹失效。

旧客户端不认识新增字段时仍可写、轮询和接受其旧流程；v1.6 服务端不得向旧 wire 字段施加新的必填要求。

### B. 记忆召回与压缩

- 保留程序召回，扩大候选上限至当前可安全输入的 300 条／30,000 非空白字符；候选包括旧章节摘要、大事记、人物事件和紧邻上一章尾段。
- Selector 改为 JSON 记忆简报：每条简报事实具有 `text` 与非空 `source_ids`，另可返回只含 Bible／记忆原文摘录和来源的 `conflicts`。后端只接受真实候选 ID、去重、按来源回填元数据；无来源、无效来源、超预算或不合形的条目一律丢弃，不能猜测补全或调和冲突。
- 将“上一章尾段”从简报预算中独立：尾段只作开场镜头承接，短上限；简报为历史事实压缩，独立短上限。初值由常量集中定义，验收时以同一固定 fixture 检查总上下文、来源和裁剪稳定性。
- Selector 固定协议禁止新增人物、事件、因果、动机、计划或未来预测。低温是辅助；来源 ID、形状校验、可展开原文和实际 Writer 输入才是防线。

### C. Writer 与确定性门禁

- 在启动任务时读取 Bible 原文一次、计算 SHA-256，并把同一不可变快照用于 Selector、Writer、Checker；写入前后核验哈希，输入或章节版本变化时取消当前结果，绝不以 Agent 文字回写 Bible。
- Writer prompt 的顺序为：世界观／人物白名单与卡片、最终记忆上下文、原始 Bible、固定执行协议；不含作者备注、目标字数或任何“达到最低字数前不得收束”的扩写措辞。
- 统一 `draft_violations` 为确定性门禁：空正文、低于4000、非正常 finish、人物白名单／重名。删除 80%–120%、目标字数、`word_count_bounds`、扩写消息、压缩／修订消息与 Reviser 循环。
- 每次 Writer 返回先创建不可覆盖候选。第一次长度类失败可从原输入整章重写一次，记录 `attempt=2`；第二次失败保留候选、恢复可编辑基线并以 `writer_minimum_failed` 或真实截断原因终止。人物或其它非长度确定性违规不自动再写，向用户展示可执行修正选项。

### D. Checker 与候选处理

- Checker 输入为原始 Bible、当前正文、允许人物及固定 JSON schema；不接受 Selector 对 Bible 的解释。检查器区分“文学性延展”与“会改变后续事实的新剧情”。
- schema 至少含 `verdict` 和逐项 `kind/draft_evidence/bible_evidence/reason`。无事实证据的项不显示为明确越界；后台需验证结构、空项和正文指纹。
- 通过确定性门禁的候选先成为可查看草稿，再进入 `checking`；Checker 完成后保存结果并将 write job 结束为可接受状态。`violation` 与 `suspect` 均不重写正文。
- Checker 上游失败也保留候选，状态诚实显示“正文已生成，Bible 检查未完成”；提供重新检查与明确忽略并接受，不将 Checker 故障伪装成正文失败。

## 4. 双端施工分块

### F. 共享模型、网络与状态

- Swift `Chapter` 保留旧 decode 字段但移除它们的编辑／指纹写入路径；新 payload 只保存标题、Bible、人物和正文／Extractor 数据。
- 扩展 Job/Candidate/MemoryContext/CheckerResult 模型，阶段改为“整理记忆、整章写作（第1/2次）、确定性验证、Bible 检查、提取”；完全移除 `revising`、`expanding` 和 Reviser 文案。
- 冷启动、轮询、缓存和跨设备对账依据 job 的 currentness 与正文／Bible 指纹处理；旧 v1.5 `revising` 历史结果仅显示为“旧版任务记录”，不得把 Reviser 重新暴露为可用角色。

### G. 编辑器、透明度与用户决策

- iOS/macOS 章节输入只显示标题、Bible、允许人物；移除目标字数、作者备注及所有“扩写／Reviser”说明。正文区明确写作要求为“至少4000字、正常结束”，不对用户承诺上限。
- 在编辑器加入折叠的“本次写作上下文”：最终记忆简报、实际尾段、来源、字符占用和 Bible 冲突提示。它显示最后一次真实 Writer 输入的工作记忆，不显示未采用候选。
- 加入“Bible 检查结果”：passed/suspect/violation、证据并列、当前／失效状态、重新检查、重新生成、编辑后检查、忽略检查并接受。Checker 不评价文风。
- 加入候选稿抽屉：保留每次完整生成的候选和校验／检查结果，选择候选不会删除其他候选。自动第二次整写与手动重生均可比较。
- 接受按钮默认仅在检查结果对当前正文有效时可用；明确覆盖操作必须二次确认并留下用户可见的覆盖状态。Extractor 完成后继续使用既有阅读分离行为。

- 每个角色页面显示：可编辑人格词、只读不可覆盖协议、恢复 v1.6 默认、模型 profile、thinking/effort、temperature 及“当前模型实际生效”的说明。
- 保存人格词不会改动固定协议；删除 Reviser 绑定后不显示失效模型配置。

## 5. 测试与验收

### 自动化

- Alembic 从 v1.5 production-like fixture 升级：保留章节、旧字段、历史 JobRun/audit；删除 Reviser 配置、创建 Checker，`heads` 唯一。
- Persona/Settings：四角色齐全、custom persona 不丢、恢复默认正确、固定协议不能通过 API 覆盖，Reviser endpoint/角色拒绝。
- Selector：有效压缩、每条有可追溯来源、无效／重复／超预算来源剔除、上一章尾段独立、实际 Writer 输入和 API manifest 一致。
- Writer：Bible hash 不变、author_note/target 不进 prompt、4000／4001边界、空／截断、仅一次完整重写、绝不扩写、不存在上限导致失败；白名单和取消／并发仍正确。
- Checker：三种结论、结构错误、上游失败保留正文、编辑后失效、明确 override 才可接受、不得修改正文；候选完整保存且选择后结果正确。
- Extractor：长摘要／状态变化／未决事项／原子记忆可写回和召回；仅接受稿被处理；人物白名单和旧动态字段回滚回归。
- iOS/macOS shared tests：旧字段仍可解码但不再写入编辑 payload，阶段／错误文案无 Reviser，透明结果及缓存恢复正确。

### 人工验收与构建

1. 用隔离库与固定模型替身走：首稿不足→一次整章重写→候选可比较；首稿超长但正常结束→继续检查；Checker 三种结论；Checker 服务失败；编辑后重新检查；明确忽略后接受；Extractor 记忆回流。
2. 两端检查 Bible 单一输入、记忆和检查抽屉、人格词编辑／恢复、长正文、断网／取消／冷启动和辅助功能；不得把真书正文或密钥用于自动化截图。
3. 运行仓库规定的 Backend pytest、Alembic heads、iOS Debug build、macOS Debug build；共享层改动必须双端通过。发版前另做 Release/signing、真实设备体验确认和生产迁移门禁。

## 6. 顺序、风险与回滚

顺序：A（含 migration）→ B/C/D 后端闭环 → E → F → G/H → 全量测试与体验验收 → 版本、部署和发布。不要先改 UI 再改 API；中间提交必须保持 migration + server API 自洽。

最大风险是 Checker 或 Selector 把推测说成事实。因此它们都只提供带来源／带证据的结果，不能自动写正文；低温不被当作正确性证明。次要风险是候选正文和记忆简报增加数据库体积，需以每章索引、明确保留策略和真实数据备份监控控制。

回滚：发布前数据库备份；代码回滚仅在 v1.6 migration 不改变旧列/旧数据、旧客户端仍可解码的前提下进行。若已写入新候选／检查数据，旧版本只忽略新增表与字段，禁止降级删除用户候选。
