## 一、安全诊断与明确分类

### Checker规则分类

让产生错误的验证分支直接赋稳定`reason_code`，不靠解析中文异常内容猜分类。可合并相同恢复方式的用户文案，但不可在私有诊断中丢掉具体规则。覆盖整个validator，而非只修此次引文分支：

| 类别 | 必须区分的具体原因 | 对作者的说明方向 |
| --- | --- | --- |
| 输出结构 | 顶层字段/类型无效、issue字段/类型/必填值无效、结论与issue矛盾 | 检查器缺少必要内容或结论自相矛盾，无法形成结论 |
| 来源 | 来源ID不存在/类型不符、引用待定状态作矛盾依据、来源引文不匹配 | 检查器引用的资料不存在、不适用或引文不一致 |
| 正文证据 | 必需正文证据缺失、`draft_evidence_not_found` | 检查器引用的文字与正文原文不一致；不是正文违规结论 |
| Bible证据 | 空Bible被引用、Bible引证缺失/不匹配、非Bible问题伪造Bible引文 | 检查器没有正确引用本章剧情要求 |
| 遗漏要求 | 非Bible依据、把缺失伪造成正文引文 | 检查器关于遗漏要求的举证方式无效 |
| 姓名输出 | 保留现有细项：行结构/值无效、分组缺失/重复/未知、人物ID不符 | 检查器未完整或正确处理人物辨别，尚不能形成检查结论 |
| 程序输入 | 冻结来源目录、姓名命中/分组目录损坏或互不一致 | 检查资料组织出现异常，不归咎于模型或作者；未知细节可追查 |
| 未知 | 非预期类型/解析/执行异常与旧`invalid_protocol` | 具体原因尚未确定；旧记录明确当时未记录细项 |

诊断保留在原JobRun/候选的私有`_validation_diagnostics`，包含reason_code，以及必要的白名单结构字段（issue序号、字段枚举、来源种类枚举、既有计数、协议版本）。不保存模型原回复、引文字串、正文、输入、自由异常repr/str或任意dict；数字有界、枚举严格校验。新错误的静态安全中文由分类映射生成。

`_checked_call`、首次Writer后的Checker、后台候选复查、当前正文复查及兼容同步`/check`必须用同一分类结果，既持久化又输出可关联日志。日志仅含真实job/check_attempt编号、环节、reason_code、白名单结构值及安全异常类型；不得把日志异常降级成“检查失败”而丢原因。未知执行异常只记录安全异常类型和位置，不输出携带正文的异常字符串。

### SOP其他阶段

对Memory Selector、Writer/确定性校验、接受与Extractor逐项核对现有生产错误分支。已具精确错误说明的保持精度（例如篇幅不足的实际字数、记忆返回结构/引用问题、归档状态冲突）；归并为unknown只能用于真正未知的异常。保留上游原有安全`http_status/block_reason/finish_reason/upstream_reason`分类，不能把限流、内容拦截、超时、截断统一描述成协议问题。

在进入terminal前保留发生错误的真实环节；未预期异常、启动失败、落库失败和服务重启同样有环节与定位编号。失败处可能是保存/启用结果，不能看job.kind就归因Writer或模型。数据库不可写时记录安全服务日志，前端明确状态尚待确认，不虚构JobRun已经成功保存。

## 二、最小接口契约

保留现有顶层`error_code/error_message`和既有返回结构；新增内容使用可选字段，旧App可忽略，新App必须兼容字段缺失。不改现有成功返回和状态机，不引入新的模型调用端点。

| 位置 | 新增/复用字段 | 契约 |
| --- | --- | --- |
| JobRun / CheckerResult `error_context` | `reason_code` | 程序产生的安全细项枚举；`checker_invalid_response`仍作为顶层兼容错误码 |
| 同上 | `failure_stage` | `preflight/selecting_memory/writing/validating/checking/accepting/extracting/persisting`；未知用缺失或`unknown`，不默认猜写作；`interrupted_phase`继续保留真实旧阶段 |
| 公开失败上下文 | `manuscript_state` | `unchanged/generated_candidate_retained/accepted/unknown`。只根据已持久化状态及当前性证明赋值；失效/无法确认时unknown，不能仅凭错误码推断 |
| 定位 | 现有`job_id/check_attempt_id`；无JobRun时`request_id` | 任务直接用已有完整编号。同步请求编号由服务器创建并进入安全日志；`X-Request-ID`返回，同时已存在的结构化detail可附`error_context.request_id`。不把编号当权限或幂等凭证 |
| 公开message | 现有`error_message` | 静态安全具体原因；不拼接private diagnostics或未验证上游正文。双端优先已识别细项，再保留其他已有精确message，再降级通用说明 |
| 恢复能力 | 既有`outcome_current/can_retry_checker/checker_source_job_id/checker_target`、archive `can_retry` | 权限仍来自既有服务端证明；不新增可与实际权限冲突的自由文本recovery_action |

公开`error_context`采取明确白名单转换，防止新增诊断直接经`_job_status_from_run`或CheckerResult流出；两种Checker公开路径和archive错误路径都验证。private `_validation_diagnostics`继续剥离；来源文本、原始模型字段不公开。静态reason_code和结构诊断在职责上分开，不用“脱敏”理由再次把所有原因折叠。

无JobRun的请求错误只补轻量关联：局限现有SOP路由的请求/异常处理与API错误解析，不改全项目网络框架。关联日志写请求编号、HTTP方法、路由模板、已知环节、稳定错误码/安全异常类型，不写完整URL查询、body、鉴权头或异常正文。最终正文状态不确定的HTTP失败/断网属于unknown，下一步是读取当前章节/任务核实，不盲目重发accept。请求未到服务器或旧后端未返回编号时明确“未取得服务端记录编号”，不能编造可检索编号；可沿用现有本机操作ID但须标作本机编号。

## 三、针对真正原因的手动Checker重试

- 继续使用现有候选单独重试入口、请求幂等标识及当前性校验：同一候选正文、快照、哈希/输入指纹与所有权不变，点击一次只调用Checker一次；不重复Selector/Writer。旧候选缺失、输入改变、已接受、其他任务运行等原阻断均保留。
- 从最新失败attempt读取安全诊断reason_code传入`checker_user_message`，不能只传顶层`checker_invalid_response`。提示以固定映射生成，不把模型回复或异常自由文本嵌回提示。
- 正文引文问题：要求逐条核对`draft_evidence`是冻结正文中的连续原文，不改写/拼接/跨来源引用；来源/Bible问题分别核对其目录与证据。结构/结论问题修对应字段及一致性；姓名分组问题才提示逐组覆盖；快照错误不假称姓名错误；旧记录或未知原因只给通用协议复核，不猜细项。
- 首次检查原有协议中补明确`draft_evidence`同样必须连续引用原正文，不因source_evidence已有要求而遗漏正文引文要求；不添加可放宽证据的变通。
- 当前正文复查只有上一失败attempt与本次完整冻结输入一致时才沿用其定向提示；改稿/改Bible/改参考资料后不得携带另一输入的错误。兼容同步检查如无对应最新失败则保持普通协议。针对异常的纠错不要求模型强行passed，真实违规仍正常返回。
- 模型再次给坏证据仍保留该次具体原因、告知无结论、供作者手动决定下一步，绝不后台循环。

## 四、双端统一说明与恢复

复用`LinoErrorPresenter`、JobErrorContext、API错误解析、LinoStores、V2DeskPresentation、现有通知历史和详情弹层；不要加新的诊断中心。iOS与macOS使用同一语义组合：简短标题显示环节/原因，详情显示原因、正文状态、操作说明和定位编号。通知本身也包含足够原因，不只显示“失败，查看详情”；横幅详情不能被通用message覆盖，过期通知可以保留历史事实但不能提供过期操作。

| 场景 | 正文说明 | 实际恢复 |
| --- | --- | --- |
| Selector/Writer/确定性校验失败 | 已确认则当前正文未被替换；新稿未产生时不谎称已保留生成稿 | 仅在允许时重试生成；配置、人物或篇幅问题指向已有具体处理入口 |
| 隐藏生成稿Checker失败 | 确认存在则“生成稿已保留，当前正文未被替换”；附“不是文章违规结论” | 仅can_retry_checker且当前输入一致时“重试检查”，沿原source_job_id |
| 当前正文Checker失败 | 正文保留、尚无可用结论；已接受正文不得被显示成未接受 | 现有“重新检查”，不能变成生成新章 |
| accept确定性拒绝 | 仅明确未提交成功时说尚未接受；保留本机/服务器正文须各自有依据 | 人物、短稿、检查、冲突按原规则处理，不能提供通用“重新生成”代替 |
| accept响应丢失/落库结果未知 | “尚不能确认是否已接受，正文状态需刷新确认” | 复用现有读状态恢复；读取失败则保留未知，不自动重发accept |
| Extractor模型/校验/落库失败 | 确认已接受则“正文已接受，仅记忆整理未完成” | 仅archive.can_retry等现行约束允许时重试归档，不重跑Bible检查 |
| 网络观察中断、启动未确认、未知/历史错误 | 明确观察状态或具体原因未知；有真实编号显示编号 | 先刷新当前任务；无证据不猜Writer阶段，不许不加判断地建议重写 |

后台终态与冷启动恢复应得到一致信息，失败attempt编号不能在转换为`WritingPhase.failed`或持久化任务摘要时丢失。通知去重按实际attempt/job，不把后一次相同reason的新失败吞掉，也不能每次轮询重复通知。任务详情的编号可选择/复制（复用已有文字交互，不增专门功能页）。底层未知字符串/DecodingError不直接作为所有解释；具体原因未知时仍给已知操作环节及读取状态建议。
